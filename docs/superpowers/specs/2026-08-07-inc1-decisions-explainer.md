## 先弄懂 6 個貫穿全文的名詞

| 名詞 | 白話 |
|---|---|
| **agent** | 使用者自己電腦上跑的小程式（`quanquant-agent`）。它負責用該使用者的永豐帳密登入 Shioaji、實際送單、收成交回報，然後透過網路把回報轉給網站。**憑證只留在使用者電腦，永遠不上網站**——這是整個架構的初衷。 |
| **in-process 模式 vs agent 模式** | in-process＝Inc0 之前的單人模式，網站自己直接連 Shioaji（你自用）。agent 模式＝下單動作外包給使用者電腦上的 agent。兩種模式用 `.env` 的 `ORDER_CHANNEL` 切換，**Inc1 鐵則：不能弄壞 in-process**。 |
| **WS（WebSocket）** | agent 和網站之間的長連線通道。agent 主動連出（穿過使用者家裡的防火牆），雙方在上面互傳 JSON 訊息。 |
| **ack（acknowledgement，回執）** | 一方告訴另一方「你剛剛那件事我收到了/做完了」。例：agent 下單後回給網站的「單號是 xxx」就是 ack。**late ack（遲到回執）**＝斷線時弄丟、重連後才補送到的 ack。 |
| **quota / reservation（配額/預留）** | 風控上限：每人每日最多幾口、幾筆。下單前先「預留」額度，確定成功才正式扣掉（confirm）、確定失敗就退回（release）。 |
| **quarantine（隔離）** | 券商回報處理失敗時不丟掉，先放進隔離區等之後重試或人工看。 |

## D1　registry 生命週期——伺服器怎麼為每個使用者準備「座位」

**在決定什麼**：多人之後，網站要為每個可下單的使用者維護一組專屬物件（連線、風控狀態、鎖、背景工人）。這條決定這些「座位」是**網站啟動時就全部建好**（eager），還是**等使用者的 agent 第一次連上來才建**（lazy）。已採用：eager。

**名詞解釋**：
- **registry**＝名冊，`user_id → 座位` 的對照表。
- **slot**＝座位，一個使用者一組的伺服器端物件包。
- **eager / lazy**＝預先建好 / 用到才建。
- **`ORDER_OWNER_USER_IDS`**＝`.env` 裡的白名單，寫哪些 user id 可以下單。座位就是按這份名單建的。

**會影響哪裡**：網站啟動流程（`web/app.py`）、下單路由怎麼找到「這個使用者的服務」。使用者幾乎無感。

**你要判斷什麼**：唯一的代價是**「新增一個可下單的人＝改 `.env` 名單＋重啟網站」**。現在本來就是這樣運作，所以等於沒有新代價。除非你想要「在網頁上直接加人、不用重啟」（工程明顯變大，Inc1 不建議），否則此條可直接同意。

## D2　agent token——使用者的 agent 怎麼證明「我是誰」

**在決定什麼**：Inc0 用一把**全站共用的固定密碼**（`AGENT_WS_TOKEN`），多人不能再共用（分不出誰是誰、也沒法單獨停掉某人）。這條決定改用：每人一枚、存在資料庫、30 天有效、可隨時作廢的通行證。

**名詞解釋**：
- **token**＝一長串隨機字串，當通行證用。agent 啟動時輸入它，網站看到就知道「這是某某的 agent」。
- **opaque token（不透明通行證）**＝字串本身無意義、純隨機，網站靠查資料庫驗證。相對詞是 signed token（字串自帶簽名、可離線驗證）——後者換發/撤銷不靈活，所以不採。
- **sha256 hash（雜湊指紋）**＝單向壓成的指紋。資料庫**只存指紋、不存 token 原文**——就算資料庫外洩，也拿不回通行證。你產生 token 時原文只顯示一次，要當場複製。
- **TTL（time to live，有效期）**＝過期自動失效，預設 30 天。
- **rotation（換發）**＝按「產生新 token」時，舊的立即作廢。
- **revoke（撤銷）**＝不等到期直接作廢。

**會影響哪裡**：資料庫新表 `agent_tokens`；orders 頁新增「Agent token」管理區（產生、只顯示一次、看最後使用時間）；agent 端輸入方式不變（環境變數或啟動時輸入）；**`AGENT_WS_TOKEN` 這個舊機制整個移除**。

**你要判斷什麼**：
1. **30 天有效期可以嗎？** 太短的話，使用者的 agent 斷線重連時 token 過期會連不上、要人工重發（半夜斷線就會積壓到早上）；太長則外洩風險窗口大。30 天是「無人值守能撐住＋定期換發」的折衷。
2. **每人同時只有一枚有效 token 可以嗎？** 意思是同一人想在兩台電腦各跑一個 agent 會互相踢掉——但本來連線就只允許一條，所以這是一致的。
3. **確定不留舊的共用密碼當後門？**（正式環境沒部署過、沒有存量 agent，留了只是風險。）

## D3　kill switch——急停按鈕是一顆還是每人一顆　⚠️ 需要你特別注意

**在決定什麼**：kill switch 是 Tier0 做的「緊急停止」開關（按下去只擋**新**單、不動已掛的單）。多人之後它應該是**全站一顆**（按了所有人都停）還是**每人一顆**？已採用：**維持全站一顆**——注意這**偏離**了交接文件原本的草圖（草圖寫「RiskGuard per-user 實例化」），是我主動改的，所以特別需要你點頭。

**名詞解釋**：
- **kill switch**＝急停開關。
- **RiskGuard**＝伺服器端的風控守門員物件（管白名單、口數上限、下單確認、急停）。盤點後發現它除了急停開關以外全是「無狀態的規則」＋「已按人記帳的資料庫」，所以拆不拆成每人一份，實質差別只有急停開關的範圍。

**會影響哪裡**：選全站一顆＝程式幾乎不動；選每人一顆＝RiskGuard 要拆成每人一份、還得**再加**一顆全站總閘（事故時總得有辦法全停），變成兩層，複雜度上升。

**你要判斷什麼**：事故時你想要的動作是什麼？
- 「**發現系統有 bug，先全部停下來**」→ 全站一顆正確（我的建議）。想停掉單一使用者＝請他把自己的 agent 關掉，天然存在。
- 「**某人亂下單，我只想停他、其他人照常**」如果是你預期的常見場景 → 才需要 per-user。可信任小圈子的 sim 階段，我認為用不到。
- 附帶語意：全站一顆時，**任何 owner 都能按**（會留誰按的紀錄）。你若想「只有你能按」，說一聲，改成 admin-only 是小改動。

## D4　command ledger——下單指令的掛號簿（三硬門檻之 G1）

**在決定什麼**：這是本次最核心的工程。修的問題：網站叫 agent 下單 → agent 真的下了 → 回執在網路上弄丟 → 網站永遠不知道結果，那筆單卡成「殭屍」，佔著配額。解法：**每筆指令先在資料庫掛號、再寄出**；agent 那邊也記一本帳防止重複執行；回執改成「送到為止」；遲到的回執到了以後照樣能把帳對平。

**名詞解釋**：
- **command**＝網站下發給 agent 的指令，三種：place（下單）、cancel（取消）、update（改單）。
- **ledger**＝帳本/掛號簿。server 端是新資料表 `agent_commands`，agent 端是它本機的 `command_ledger` 表。
- **冪等（idempotent）**＝同一件事收到兩次，效果等於一次。斷線重連會重送指令和回執，冪等保證「重送不會變成下兩張單」。
- **CAS（compare-and-swap）**＝資料庫的「先檢查再改」原子操作。兩個處理程序同時搶著更新同一筆，保證只有一個成功——這是防重複記帳的底層機制。
- **兩維終結模型**＝把「回執送到了沒」（transport 維度）和「單子到底成了沒」（業務維度）分開記。逾時只代表「沒收到回執」，不代表「單沒成」——混為一談正是 Inc0 殭屍單的根源。
- **expiry / expired（指令過期）**＝指令帶保存期限（預設 120 秒），太晚才送到 agent 的舊指令會被拒絕執行（免得兩天前的下單指令在今天成交）。

**會影響哪裡**：網站 DB 新表、agent 本機 SQLite 加表、下單/取消/改單三條內部流程重寫（**你看到的操作介面不變**）、斷線重連後自動補送與對平。

**你要判斷什麼**：機制本身是 codex 開的硬條件、沒有替代方案好選。要你點頭的是一個營運取捨：**如果使用者的 agent 一直不重連，他那筆「結果不明」的單和被佔的配額，會保留到當日收盤自動歸零，網站不會自作主張判它死**（因為券商那邊可能真的成交了，判死＝低估曝險＝危險）。也就是說：極端情況下某人當天會有幾口額度被卡住，換來的是絕不重複下單。接受嗎？

## D5　RawInbox scope——回報進來時，怎麼知道「這是誰的」

**在決定什麼**：券商回報（成交、委託狀態）進到網站後先落在 `raw_inbox` 表再處理。Inc0 這張表**沒有「屬於誰」的欄位**（單人不需要），多人必逼著加。解法：回報在 agent 端產生的當下就蓋上「帳號＋模式」的章，網站落地時再蓋「使用者」的章，之後所有處理都按章行事。

**名詞解釋**：
- **RawInbox**＝原始回報收件匣（先存原始 JSON、再慢慢處理，處理失敗也不丟資料）。
- **scope**＝歸屬（這筆資料屬於哪個 user、哪個永豐帳號、sim 還是 real）。
- **immutable（不可變）**＝章在資料產生當下蓋死，之後斷線重送、換帳號都不會變。這保證「舊帳號的回報永遠記在舊帳號」。
- **mapper**＝把券商原始欄位翻譯成我們資料表欄位的轉換器。Inc0 的轉換器會去讀一個全域變數拿帳號（多人下會拿錯人），改成讀「列上蓋的章」。
- **dead-letter（死信）**＝確定永遠處理不了的回報（例如帳號對不上、疑似偽造），標記後封存：不再重試、不再擋人、只留稽核紀錄＋告警一次。

**會影響哪裡**：`raw_inbox` 加 4 個欄位；agent 本機暫存箱加欄位；回報處理背景工人改成**每人一個、只碰自己的**；「換帳號防呆」從全站擋改成只擋自己。

**你要判斷什麼**：純技術修正，沒有商業取捨。只有一件事要知道：你本機 `quanquant.db` 有 5 筆七月留下的歷史隔離列，**換永豐帳號測試前要人工清掉**（之後會給明確指令）。

## D6　鎖拆分——A 的慢動作不再讓 B 排隊

**在決定什麼**：Inc0 全站共用一把「序列化鎖」（保證同一時刻只有一件事在動下單狀態）。多人共用一把＝A 在對帳時 B 的下單要排隊。拆成每人一把。

**名詞解釋**：
- **supervisor 鎖**＝那把序列化鎖的名字。
- **head-of-line blocking（排頭堵塞）**＝隊伍最前面卡住、後面全部等。拆鎖就是消掉「跨使用者」的排頭堵塞。
- **watchdog（看門狗）**＝定期巡邏的背景任務（重試隔離列、收斂不明配額等），也跟著改成每人一份。

**會影響哪裡**：內部物件的實例化方式；順手補一個 Inc0 的小缺（agent 模式漏了「確認 token 清理」背景任務）。

**你要判斷什麼**：無商業取捨。保留一個已知可接受項：**同一個使用者自己的**對帳仍會排隊自己的下單（跟 Inc0 單人時行為一樣，不影響別人）。

## D7　協定版本——「硬 bump v2」是什麼意思　⚠️ 需要你特別注意

**在決定什麼**：agent 和網站在 WebSocket 上講話的**訊息格式**是一份雙方的約定，叫**協定（protocol）**，有版本號。**v1**＝Inc0 定的第一版（agent 登入時會自報「我講第 1 版」）。Inc1 因為要加欄位（回報蓋帳號章、健康訊息帶計數器）和新訊息型別（查口數、查詢結果、拒絕通知），格式變了，升成 **v2**。**bump**＝把版本號往上調。**硬 bump**＝直接切到 v2、**不向下相容**：網站聽到有 agent 講 v1，直接拒絕連線並提示「請更新 agent」。相對的「軟」做法是網站同時聽得懂 v1 和 v2（寫一層相容轉換），讓舊 agent 繼續用。

**會影響哪裡**：`agent_protocol.py` 訊息定義改版；每個使用者要更新 agent（對技術型使用者就是 `git pull && uv sync` 一次）才能連上新版網站。

**你要判斷什麼**：**相容舊版保護的對象目前不存在**——正式環境沒部署、世界上唯一的 agent 在你電腦上。寫相容層是純浪費。你只要確認一個原則：**未來協定改版時，你可以要求所有使用者更新 agent**（可信任小圈子、人數個位數，應該沒問題）。如果你反而想要「網站升級後、還沒更新的 agent 能繼續用一陣子」，才需要否決此條（成本：每次改版都要維護兩套格式）。

## D8　unknown 配額自動解除（三硬門檻之 G3）

**在決定什麼**：「改單送出去、結果不明」的時候，被佔住的額度要能**自動查證、自動收斂**，不必人工進資料庫。Inc0 在 agent 模式下這件事整段停用（人工處理），Inc1 恢復。

**名詞解釋**：
- **unknown（不明）**＝指令送出去，既沒收到成功也沒收到失敗（通常是逾時）。
- **query_qty（查口數）**＝新的下行指令：網站請 agent 去問券商「這張單現在到底幾口」，用答案反推改單成沒成。
- **resolver（解決器）**＝專門收斂不明狀態的邏輯。**終態 resolver**＝當那張單已經走到最終狀態（全部成交/已取消）時的收尾邏輯。
- **單飛規則（single-flight）**＝同一張單同時只允許**一筆**結果不明的改單存在，第二筆改單要等前一筆確定才准送。沒有這條，查口數會分不清「查到的 3 口」是哪一次改單造成的。

**會影響哪裡**：協定加查詢訊息；agent 加查詢功能；watchdog 加收斂邏輯；改單入口多一道「前一筆改單結果未定」的擋板。

**你要判斷什麼**：一個保守取捨：**查證不出來的時候，寧可把額度「當作已用掉」（confirm）也不退回（release）**。理由：多算你的當日用量（頂多讓你少下幾筆）安全；少算（可能讓你超過風控上限）危險。接受嗎？另外「同一張單第二筆改單要等前一筆確定」在正常網路下無感（幾秒內），只有斷線時才會被擋——可以嗎？

## D9　offline 行為與 healthz 語意　⚠️ 需要你特別注意

**在決定什麼**：兩件事。①使用者的 agent 沒開時，他按下單會發生什麼；②監控用的健康檢查網址 `/healthz` 的意義要改。

**名詞解釋**：
- **offline**＝該使用者的 agent 沒連線（關筆電、關程式）。
- **badge**＝orders 頁上的連線狀態小標示，改成顯示「**你自己的** agent 狀態」。
- **healthz**＝給監控系統看的網址：回 200＝正常、503＝故障（監控看到 503 就告警）。Inc0 單人時「agent 沒連」＝「下單系統壞了」→ 503 合理。多人時「有人關筆電」是**常態**，不能再讓它把整個網站標成故障。
- **fail-fast（快速失敗）**＝agent 沒連線時，下單請求直接吃「你的 agent 未連線」錯誤，不排隊、不暫存。
- **lease（租約）**＝agent 要定期回報心跳，太久沒回報（超過租約期）就視為不健康，即使連線看起來還在。
- **failstop**＝agent 本機存檔壞掉（例如磁碟滿）時的自我停機保護（三硬門檻之 G2）：拒絕新指令＋上報「我壞了」，網站亮紅燈＋Telegram 告警。

**會影響哪裡**：UI badge、`/healthz` 判定邏輯、Telegram 告警多一種（failstop）。

**你要判斷什麼**：
1. **healthz 語意變更**：以後「healthz 503」只代表**網站本身**壞了；「某人的 agent 斷線」看 UI badge 和告警，不會觸發 503。你的監控要按這個理解來看。接受嗎？
2. **offline 擋新單**：agent 沒連線就直接報錯，不做「排隊等連上再自動送出」。排隊很危險——等連上時價格早就變了。接受嗎？

## D10　帳號綁定唯一性——一個永豐帳號只能屬於一個人

**在決定什麼**：回報和委託的對應是靠「永豐帳號＋單號」，**天生不含使用者**。如果 A 和 B 先後用同一個永豐帳號登入，B 的回報會對到 A 的委託，資料互染。解法：新表記「永豐帳號 ↔ 網站使用者」的綁定，**先綁先贏**，別人再用同一帳號登入直接拒絕。

**名詞解釋**：
- **binding（綁定）**＝永豐帳號和網站使用者的一對一對應。
- **backfill（回填）**＝啟用多人模式前，先掃歷史委託資料，把「這帳號歷史上是誰在用」預先建進綁定表——防止新來的人「先綁」搶走老使用者的帳號。
- **fail closed（保守失敗）**＝發現歷史資料裡同一帳號竟屬於兩個人時，**拒絕啟動**多人模式、要求人工裁決，而不是猜一個。
- **UNIQUE(broker, account)**＝資料庫唯一性約束：同一券商＋帳號在綁定表裡只能有一列，資料庫層強制、程式繞不過。

**會影響哪裡**：新表；agent 登入網站時多一道檢查；被拒的人會看到「此帳號已綁定其他使用者，請找管理員」。解綁 Inc1 不做 UI，找你手動處理。

**你要判斷什麼**：
1. 「先綁先贏＋解綁找管理員（＝你）手動」可以嗎？
2. **你的圈子裡有沒有「兩個人共用同一個永豐帳號」的情境？** 有的話這設計會直接擋掉——這是刻意的（共用帳號必然資料互染），需要先跟大家講好一人一帳號。

---

## D11　agent 本機暫存箱的格式升級

**在決定什麼**：agent 在使用者電腦上有個小 SQLite 檔（**buffer/outbox**，暫存箱）：回報先存這裡、確認網站收到才劃掉——這是「斷線不丟資料」的關鍵。Inc1 要改它的表結構（**schema**），這條決定升級方式：檔案裡記一個**版本號**（schema_version），新版 agent 啟動時發現版本不對——暫存箱是**空的**就直接砍掉重建；**還有沒送出的資料**就拒絕啟動並提示（防止升級動作把沒送出的回報弄丟）。

**會影響哪裡**：`agent/buffer.py`；使用者升級 agent 後第一次啟動，極少數情況會看到「暫存箱還有未送資料，請先用舊版送完」的提示。

**你要判斷什麼**：無商業取捨，確認這種保守行為（寧可拒啟、不冒丟資料風險）可接受即可。

## 總結：三條最需要你表態的

| 決策     | 一句話                       | 預設方案                      |

| **D3** | 急停開關全站一顆還是每人一顆？           | 全站一顆（偏離原草圖，需明確點頭）         |
