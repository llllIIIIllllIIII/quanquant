1. **帳戶權益／保證金／可用資金**：整個專案沒有任何 equity／margin／balance 的概念。

2. **規則引擎**：`alerts/engine.py` 是價格條件告警，沒有「損益／行為達標即觸發」這一類規則。

4. **時間性的帳戶狀態**：沒有「某段期間內禁止下單」這種帶到期時間的狀態。

## 功能清單

## F0 — 緊急停止下單：改為「只擋開倉、允許平倉」

**狀態**：產品邊界已定案（2026-08-28），掛單漏洞的處理已深掘（見「設計風險」節），細部規格待工程端回饋

### 產品邊界（使用者 2026-08-28 定案）

「**本人／帳號使用者可以隨時解除並恢復下單。**」

目的不是建立一個無法逆轉的強制封鎖機制，而是讓使用者在意識到自己目前的交易狀態不佳時，
可以主動停止新增交易，替自己創造一段喘息、重新思考與恢復判斷能力的時間。
不可逆的約束是 F1（冷靜期）的職責，F0 不往該方向加強。

### 要解決的問題（使用者原話）

> 緊急停止下單想解決的情境，會比較像是「過度交易」、「頻繁進出」，
> 一直連輸或是被連續多空雙殺的情緒狀態。

也就是說，這個開關的定位**不只是系統／行情異常時的技術性煞車**，
更是交易者在情緒失控當下能立刻踩下去的那一腳。它與「交易冷靜期」（F1）的差別在於：

| | 緊急停止下單（F0） | 交易冷靜期（F1） |
|---|---|---|
| 使用時機 | **當下**就要停 | 決定「今天到此為止」 |
| 時效 | 無時效，手動解除 | 有時效，時間到才恢復 |
| 解除 | 可隨時解除 | **不可提前解除** |
| 情境 | 過度交易、連輸、情緒失控 | 賺錢後亢奮、大賠後需要休息 |

### 行為變更

**現況**：kill switch 開啟後，`RiskGuard` 拒絕**所有**新委託，不分開倉或平倉。
→ 這代表使用者在停止狀態下**也不能平掉手上的部位**，而「情緒失控」時往往還有部位在場上。

**期望**：只擋**開倉**，**允許平倉**。

### 解除權限（使用者已定案）

**帳號使用者本人，隨時可以解除。**

> 這就是「人為的意識到自己的交易狀況現在不大好，所以給自己一些喘息的空間，
> 跟有機會去思考的時間」。

也就是說 F0 的定位是**本人的自我煞車**，不是管理者的管制手段。實作注意：
現行 kill switch 是**全域、owner-only**（`RiskGuard.assert_owner`）；定位改為自我煞車後，
授權語意應是「帳號使用者本人可啟動與解除」——單一交易者部署下與現行 owner 相同，
但文件層面先講清楚，將來多使用者時這應該是 per-user 狀態，不是全域開關。

### 既有開倉掛單的處理（已討論，附實務風險推理）

問題：緊急停止只擋新的開倉，但**啟動前已掛出的開倉單仍會成交**，「停止」有漏洞。

三個選項的實務風險評估：

| 選項 | 風險 |
|---|---|
| (a) 維持不動，畫面明說 | 漏洞持續存在，靠使用者自己記得 |
| (b) 啟動時提示使用者自行撤單 | 情緒失控當下要人逐筆操作，摩擦太高 |
| (c) 靜默自動撤開倉掛單 | **撤單會失敗、會部分成功、會與成交賽跑**（撤單指令到達前剛好成交）。靜默執行會讓使用者以為已乾淨，實際可能留單 |

**建議採折衷：啟動彈窗揭露 ＋ 一鍵批次撤銷（需使用者親手按）。**

- 啟動時彈窗列出所有開倉掛單（`octype=New`；**`Auto` 在空倉時即為開倉意圖，保守歸入**），
  附「同時撤銷這 N 筆開倉掛單」的動作。
- 批次撤銷的**結果必須回報**：幾筆成功、幾筆失敗、幾筆來不及撤已成交——不可只回「已撤銷」。
- 使用者跳過撤單時尊重其選擇，但下單頁與風控頁需顯著標示「仍有 N 筆開倉掛單可能成交」。
- 既然 F0 定調為「本人隨時可解」的自我煞車，此漏洞不必做到密不透風——
  **看得見、一鍵可處理**即可，剩下交給人的判斷。

#### 深掘：折衷方案本身的殘餘風險（使用者 2026-08-28 要求重新分析；設計紀錄，保留勿刪）

「彈窗揭露＋一鍵批次撤銷」定案後，仍有五個殘餘情境要在規格裡處理：

| # | 殘餘風險 | 情境 | 防呆規則 |
|---|---|---|---|
| R1 | **批次撤銷不是全有全無** | N 筆裡撤成 3、失敗 1、來不及撤已成交 1 | 結果逐筆回報（成功／失敗／已成交／**狀態不明**四類）；「狀態不明」的單要持續追蹤到終態，期間橫幅維持警示，不可只回「已撤銷」 |
| R2 | **撤單與成交賽跑** | 彈窗顯示到按下撤銷之間的幾秒內，掛單成交了 | 彈窗內容視為快照；動作完成後重查一次並顯示最終狀態。停止期間任何開倉單成交都要**顯著通知**（「停止期間開倉單成交：多 2 口 @xxxxx，你隨時可以平倉」），不是靜靜出現在列表 |
| R3 | **跳過撤單後的改單漏洞** | 使用者留著開倉掛單，之後在停止期間把價格改到市價附近逼它成交＝變相開倉 | 停止期間**開倉掛單只允許撤銷**，禁止改量／改價；平倉單改單不受限 |
| R4 | **Auto 倉別掛單的歸類** | 揭露清單要分開倉／平倉，但 Auto 單判不出來 | 空倉時 Auto＝開倉意圖，歸入開倉；**有部位時 Auto 單獨列為「無法判定」一類**，附說明，讓使用者自行決定撤不撤——不可硬塞進任一邊造成誤導 |
| R5 | **啟動瞬間的 in-flight 委託** | 按下啟動的同一秒，另一個分頁／裝置正在送出開倉單 | 攔截點在 server-side RiskGuard（下單時查狀態），不靠 UI 停用；毫秒級競態接受，因為傷害上限是一張單、且事後看得見 |

這些規則的共同精神：**系統不代替使用者按撤銷（那是選項 c 被否決的理由），
但要把「按下去之後真實發生了什麼」誠實、即時、逐筆地照給使用者看。**
折衷案的價值在透明，透明斷掉它就退化成選項 (a)。

### 設計風險、濫用方式與取捨（設計紀錄，保留勿刪）

#### F0 整體漏洞盤點（依實際交易情境）

| # | 漏洞 | 情境 | 對策 |
|---|---|---|---|
| L1 | **解除零摩擦** | 情緒失控者按下停止，30 秒後又解除繼續凹單——啟動與解除都是一次點擊，約束力趨近於零，還提供「我有煞車」的虛假安全感 | 解除加「使意識化」的摩擦，不是加難度（見下方防呆設計） |
| L2 | 既有開倉掛單仍會成交 | 停止前掛的突破單在停止期間成交 | 已決議：啟動彈窗揭露＋一鍵批次撤銷＋逐筆結果回報（含殘餘風險 R1–R5，見上節） |
| L3 | 倉別 Auto 無法事前判定開平 | Auto 單在停止期間送出，成交後才知是開倉 | 停止期間 Auto 一律擋（fail closed），UI 鎖定倉別為「平倉」 |
| L4 | 假平倉：標記 Cover 但無對應持倉 | 空倉時送 Cover 單繞過開倉禁令 | 風控層驗證「平倉口數 ≤ 該方向目前持倉」，**送出時與（未來條件單）觸發時各驗一次** |
| L5 | 改單變相開倉 | 對未撤的開倉掛單加量、追價逼成交 | 同 R3：停止期間開倉掛單只准撤銷 |
| L6 | 開倉型條件單觸發（未來） | 停止前設好的突破進場單在停止期間到價 | 觸發時同樣過 RiskGuard 被擋；UX 呈現為「已暫停」，見「交互檢查」節 |
| L7 | **場外通道** | 使用者改用券商官方 App／直連 Shioaji 下單 | 技術上擋不住（我們不控制券商端）。誠實揭露「此停止僅對本系統下單有效」；場外回報若抵達會因無對應委託進 quarantine（已驗證，不入帳）——以 quarantine 計數提示；是否收得到場外回報需工程實測 |
| L8 | 多裝置／直接打 API | 換瀏覽器或直接 POST 端點繞過 UI 停用 | 停止是帳戶層級狀態，攔截在 server-side RiskGuard（單一稽核點）；UI 停用只是體驗層 |

#### 防呆設計（建議規格）

- **啟動要快**：一顆明顯的按鈕＋揭露彈窗（持倉／掛單／禁止與允許清單），可選填一句「停止原因」。
- **解除要「有意識」而非「困難」**：解除時顯示啟動時間與已經過時長、啟動當下填的原因、
  今日已啟動／解除次數；確認文案要求主動點選「我已恢復冷靜，恢復下單」。
  （使用者 2026-08-28 定案：**不加**「解除後延遲 N 分鐘才生效」的緩衝——忠於「隨時可解」
  的邊界；強度分層下，更強的約束交給 F1，不在 F0 疊加。）
- **停止期間的畫面狀態**：全站可見的紅色橫幅、開倉側控制項停用、倉別鎖定「平倉」。
- **軌跡即防呆**：每次啟動／解除寫入稽核（時間、原因、間隔），風控頁顯示歷史；
  短時間內反覆啟動／解除（例如 1 小時內 ≥3 次）時，主動建議升級為 F1 冷靜期。
- **可選通知**：啟動／解除推送 Telegram——外部可見性本身就是約束。

#### 自主權 vs 風控有效性：取捨原則（設計紀錄）

採**強度分層**：F0 是軟煞車（隨時可解，靠摩擦與自我覺察），F1 是硬煞車（時間鎖）。
兩者不混合——把 F0 的解除做難，會侵蝕「狀況排除後要能立刻恢復」的正當需求；
把 F1 做軟，防衝動效果歸零。F0 的有效性來源不是「擋住使用者」，而是：

1. 打斷「點擊即成交」的機械循環；
2. 在解除的瞬間強制一次自我對話；
3. 留下可回顧的軌跡（含停止期間的場外行為）。

系統的職責是**插入深思，不是築牆**；牆是 F1。擋不住的（L7）就映照——不懲罰，
但讓使用者看見自己繞過了自己。

#### mode 範圍（使用者 2026-08-28 定案）

**只擋 real**。sim 沒有實際金錢損害，甚至可作為停止期間的情緒出口。
實作注意：F0 狀態應為 per-mode（現行 kill switch 是全域，需調整）。

### 必須先決定（實作陷阱，請務必處理）

（第 1、2 項的方向已隨上方漏洞盤點 L3／L4 定案，原文保留供工程端理解脈絡；第 3 項已決議。）

1. **倉別「自動（Auto）」怎麼辦？**
   倉別有三種：`New`（新倉）／`Cover`（平倉）／`Auto`（自動）。
   `Auto` 在**送出前無法判定**是開還是平——系統是等成交回報進來、比對當下持倉才決定
   （`broker/position_tracker.py`），而且雙向都有部位時會直接 `Auto 歧義` fail closed。
   → 建議：停止狀態下 **`Auto` 一律擋（fail closed）**，並在 UI 把倉別鎖成「平倉」或明確提示改選。
2. **防止用「平倉」標記繞過**：
   使用者可以送一張標記為 `Cover`、但其實沒有對應持倉的單。
   → 風控層必須再驗一次「**平倉口數不得超過該方向的目前持倉**」，否則「只擋開倉」形同虛設。
3. ~~既有掛單怎麼處理~~ → 已決議，見上方「既有開倉掛單的處理」。

## F1 — 交易冷靜期／帳戶暫時停用

**狀態**：使用者已描述完整情境與啟動條件，實作細節待確認

### 要解決的問題（使用者原話）

> 交易冷靜期我設想的情境，有賺錢、也有大賠的場景。
>
> 通常**賺錢後，交易慾望有時候會增加、手單的風控能力也會下降**，這時候就會需要一個讓交易員
> 「下班」的按鈕，透過具時效性的交易冷靜期，讓交易員的身心有機會回復，
> 而不是變成「過度交易」的狀態。至少，我個人是會遇到這樣的問題。
>
> 再來是**大賠，就更需要休息跟冷靜了**。如果在精神狀態、心態、方向偏誤的狀態，就很容易釀成大錯。

換句話說，這不是一個防止系統出錯的機制，而是**讓人有機會離開交易台**的機制。
兩種情境都成立：贏到亢奮、輸到失衡，兩者都會讓風控能力下降。

### 構想

使用者自己啟動，選擇時長（1 小時／1 天／1 週／自訂），期間內無法下單。

**關鍵設計原則（使用者指定）**：**啟動要容易，解除要困難或不可逆。**
若能隨時一鍵取消，防衝動的效果就歸零——一旦啟動就無法提前解除，只能等時間到，
才真正約束得到「衝動當下的自己」。

### 啟動條件：必須空倉（使用者指定）

> 我設想的交易冷靜期，要啟動時最好需要「空倉」的狀態。如果這時候還有倉位在裡面，
> 除了拒絕這個交易冷靜期的受理，也要跳出「你還有倉位在裡面」
> （實際跳出的訊息可以因應實際還有哪些倉位留著）。

- [ ] 啟動前檢查部位；有部位則**拒絕受理**。
- [ ] 拒絕訊息要**列出實際持倉內容**（商品、方向、口數、均價），不是一句籠統的「你還有倉位」。
- [ ] 拒絕時提供**前往處理部位的入口**——大賠情境下往往正好還有部位，
      使用者是在最需要冷靜的當下被擋住，這時候只給一句拒絕會讓人更焦躁。

### 啟動彈窗（使用者已確認）

啟動冷靜期前的彈出式視窗，必須**同時揭露**（第 3 點為使用者 2026-08-28 新增指定）：

- [ ] 目前**未平倉部位**（商品、方向、口數、均價）
- [ ] 目前**未成交掛單**（商品、方向、口數、價格、倉別）
- [ ] 啟動後**哪些操作會被禁止、哪些仍然可以使用**——
      禁止：開倉（新增部位）、提前解除；仍可用：平倉、撤單、查看行情／交易日記／績效。

有任一部位或掛單存在即拒絕受理，並在同一個彈窗提供前往處理的入口。

條件單上線後，啟動條件同步擴大為 **clean slate：無部位＋無未成交掛單＋無任何有效條件單**——
開倉型條件單是第三種會生出部位的東西（見 F6 T4）；無部位卻掛著的孤兒停利／停損
也要求先清理，彈窗一併揭露（詳見「交互檢查」第 2 點）。

### 平倉安全閥（使用者已定案：保留）

冷靜期內**平倉永遠開放**。「不可提前解除」指的是**開倉的權利**，不是應變的能力。

### ⚠ 測試端發現的缺口：空倉不等於安全

**啟動當下空倉，不代表冷靜期內不會生出部位**——先前掛出去、還沒成交的委託仍然有效，
在冷靜期內成交就會產生部位，而使用者此時處於不能下單的狀態。

建議：

1. 啟動條件改為「**無部位 _且_ 無未成交掛單**」，或在啟動流程中要求先處理既有掛單。
2. **保留平倉安全閥**：即使在冷靜期內，也必須允許平倉。
   被鎖在「有部位卻不能平」是所有情境裡最糟的一種，比讓使用者提早結束冷靜期還糟。
   （這與「不可提前解除」不衝突：不能解除的是**開倉**的權利。）

### 冷靜期內仍可能出現部位的來源（平倉安全閥必須存在的理由；設計紀錄）

啟動條件即使做到 clean slate，冷靜期內部位仍可能從這些地方生出來：

1. 啟動前的狀態同步落差（成交回報延遲、對帳補進的本系統委託進展）；
2. （條件單上線後）漏擋的開倉型觸發。

**場外通道的修正（2026-08-28 查證後更新）**：券商官方 App／直連 Shioaji 開的倉，
其回報即使抵達本系統，也會因**比對不到對應委託而進 quarantine 隔離**
（`inbox_worker.py:182-194`）——**不會**成為系統部位。因此場外單的風險型態是
「**帳實不符**」（系統帳上的未平倉與券商實際不一致），而不是「冷靜期內冒出部位」。
連鎖效應：「平倉口數 ≤ 系統持倉」的驗證會擋掉在本系統平場外倉——場外的帳只能回場外收尾。
建議：以 quarantine 計數在畫面提示「偵測到 N 筆非本系統委託的回報」；
Shioaji 是否會把場外委託的回報推送到本 session，列為**工程實測項**。

偵測到冷靜期內出現新部位（或場外回報）時：顯著通知使用者、開放平倉路徑、記錄事件；
冷靜期結束的回顧摘要要把這段列出來——**不懲罰，但讓使用者看見自己繞過了自己**。

### 期滿行為（建議）

- 時間到自動恢復下單權，並通知使用者（畫面＋Telegram）。
- 冷靜期間被暫停的開倉型條件單**不自動恢復**，需逐一手動重新啟用——
  一週後行情已不同，過期的突破單在解除瞬間直接觸發是意外開倉，比不恢復更危險。

### 其他必須先決定

- ~~由誰可以強制解除~~ → **已定案（使用者 2026-08-28）：啟動後短暫反悔窗**——
  啟動後 5 分鐘內可取消（化解誤觸），逾時即完全鎖死到期滿，**任何人（含 owner）不可提前解除**。
  設計紀錄：owner 後門在單人部署下＝給自己留後門，防衝動效果打折，故不採；
  反悔窗長度以 5 分鐘為預設，可再調。
- 冷靜期是否跨裝置／跨登入生效？（應該是帳戶層級的狀態，不是瀏覽器層級）

（掛單的處理已由啟動條件涵蓋：無掛單才受理，故不存在「冷靜期中既有掛單」的情境；
 平倉安全閥已定案保留。）

### 前置

需要「帶到期時間的帳戶狀態」（見現況盤點第 4 點）。

## F2 — 緊急停止的變體：一鍵清倉

**構想**：除了停止新單，再提供一鍵平掉所有部位。

⚠ **這是本文件裡風險最高的一項，建議最後做、或先不做。**

現行 kill switch 刻意**不**自動撤單／平倉，理由已寫在程式註解：自動撤單危險，留給人工判斷。
一鍵清倉把這個風險放大一級。

**必須先決定**：
- 用**市價**還是限價平倉？市價保證成交但滑價不可控；限價可能平不掉，在急跌時等於沒平。
- **部分成交**怎麼處理？剩餘量要不要追價？追幾次？
- 平倉單本身**失敗或狀態不明**時要不要重試？（重試設計錯誤會變成反向開倉 → 兩倍部位）
- 與既有掛單的關係：先撤單再平倉？兩者的順序錯了會出現「撤單還沒生效就又送出平倉單」。

**前置（硬性）**：現況第 3 點的**契約月缺口必須先修**。
部位資料只有 `symbol`，一鍵清倉在換月前後可能對**錯誤的契約**送單，後果比不做這個功能更嚴重。

## F3 — 損益型自我監控與提醒

**構想**：
- 當日累計虧損達到設定值時通知
- 連續虧損筆數達到設定值時提醒
- 交易頻率異常提醒

**現況對照**：損益資料與績效指標都有（`journal/pnl.py`、`stats/metrics.py`），
通知管道也有（Telegram／瀏覽器 toast），缺的是**規則引擎**與**設定介面**。
交易頻率目前只有硬上限（每日 20 筆直接拒絕），不是提醒。

**這是本文件裡最容易先做的一項**——以**損益金額**為基準的規則不需要新的資料來源。

**已定案（使用者 2026-08-28）**：

- **觸發後行為：提醒＋一鍵進入冷靜期**。注意冷靜期的啟動條件是 clean slate——
  觸發當下若有部位或掛單（大賠場景幾乎必然有），按鈕應改帶 **F0 緊急停止**
  （或先帶到部位處理入口），不可讓使用者按了卻被拒絕。
- **通知管道：畫面內（SSE toast）＋ Telegram 都發**——盤中盯盤畫面立刻看到、
  離開螢幕時 Telegram 補上；風控訊息寧可重複、不可漏接。
- **「當日累計虧損」的損益範圍：已實現＋未實現合計**（mark-to-market）。
  理由（設計紀錄）：「大賠需要休息」的典型狀態是抱著大筆浮虧不肯砍——損失還沒實現、
  人已在最危險的狀態，只看已實現會剛好漏掉最需要提醒的場景。
  數學已有現成：`journal/pnl.py::unrealized_pnl`（現價 × 部位 × 點值），缺的只是接線。
  必要配套：
  1. **去抖動**：未實現損益每 5 秒變動，門檻附近會反覆穿越——單次觸發＋回升一段距離
     後才重新武裝，否則通知洗版；
  2. **訊息拆列**：「已實現 -8,000 ＋ 未實現 -5,200 ＝ 合計 -13,200」，
     一眼分清已鎖定與還在場上的部分；
  3. 報價停滯時未實現是舊價算的，通知需帶資料時間（沿用既有 freshness 判定）。
  連續虧損筆數天然以已實現（round-trip）計，不受此決策影響。

**「當日」的定義（使用者 2026-08-28 定案）**：沿用專案既有的 `trading_day` 概念——
以交易日（含夜盤跨日）為準。

## F4 — 資金比例型風控（虧損達總資金 X%）

**構想**：當日虧損達到總資金的某個百分比時，跳出紅字或強制介入。

⚠ **目前缺分母，這是產品決策而非工程問題。**

系統沒有任何帳戶權益／可用資金的概念。要做這個功能必須先決定「總資金」從哪裡來：

| 來源 | 優點 | 代價 |
|---|---|---|
| 券商 API 取帳戶餘額／權益 | 真實、自動 | 需確認 Shioaji 提供哪些欄位、更新頻率、以及連線失敗時的降級行為 |
| 使用者自行輸入初始資金 | 立刻可做 | 會過期、需要人工維護，數字不準時風控形同虛設 |

**分母定案（使用者 2026-08-28）**：real 模式以**券商帳戶總保證金**為「總資金」。
Shioaji 期貨帳戶有 margin 查詢可用；具體取哪個欄位（總保證金／權益數／可用保證金）、
更新頻率、以及連線失敗時的降級行為，由工程端查證後回饋再定。
sim 模式沒有券商帳戶、天然缺分母：建議 **sim 先不做 F4**（損益金額型的 F3 已可涵蓋 sim），
日後若要做再考慮手動輸入虛擬本金。

順序維持：F3 先做，F4 隨後。

## F5 — 操作摩擦（Friction）機制

**構想**：
- 下單前強制二次確認
- 停用市價單（只能用限價單交易）
- 單日首筆交易前顯示風險提示
- **停損單向鎖定**（使用者 2026-08-28 新增，原話「不可拉低風控」）：
  勾選後，停損價位**只能往減少虧損／保護獲利的方向調整，不可往擴大虧損的方向放寬**
  （多單停損只能上移、空單停損只能下移）。
  - 勾選文案建議：「停損只緊不鬆——停損價只能朝保護方向調整，不能放寬」（語句可再修）。
  - 生效範圍：啟用時**全時段生效**，不限停止／冷靜期間；未啟用時維持預設行為
    （放寬停損＝放行＋記錄＋警示，見交互檢查第 3 點）。
  - **防繞過（設計紀錄，關鍵）**：只擋「修改」會被「先撤掉停損、再重掛一張更寬的」繞過——
    啟用時停損單**不可單獨撤銷**，僅能收緊、或隨部位平倉自動消滅。
  - 關閉此偏好本身需意識化確認＋記錄（同 F0 解除的精神），不做時間鎖。
  - 與移動停損天然相容：trailing 本來就只朝保護方向移動。
  - 勾選位置：風控偏好區，落點待定（傾向風險控管頁、與 F5 其他開關同區）。

**現況對照**：
- 二次確認：已有（real 模式），但是**系統決定**的，不是使用者可開關的偏好。
  要做的是「把它變成使用者可自選、且可套用到 sim」。
- 停用市價單：完全沒有帳戶層級的鎖定，目前是每次下單自選。
- 單日首筆風險提示：沒有。

**已定案（使用者 2026-08-28）**：定位為**使用者偏好**——自己開給自己的自我約束，
與 F0／F1「自我煞車」的定位一致，控制項放風險控管頁。
（owner 帳戶政策層留待未來多使用者時再升級；單人部署下兩者無差異。）

## F6 — 條件單（停利／停損／移動停損）與視覺化調整

**狀態**：使用者 2026-08-28 確認**列入後續規劃**；本節先盤點與風控功能的衝突與陷阱，規格另開文件

### 確認列入規劃的功能（使用者 2026-08-28）

- 下單時預先設定**停利**點位
- 下單時預先設定**停損**點位
- **移動停損**（Trailing Stop）
- K 線圖上**視覺化停利線**
- K 線圖上**視覺化停損線**
- **滑鼠拖曳**停利／停損線直接調整價格
  （拖曳＝修改一張真實委託；KLineCharts 釘版 v9.8.12 的 overlay 拖曳能力需先驗證，見 T6）

### 與風控功能的衝突檢核（本節的重點）

#### T1 — 觸發引擎跑在哪裡、可靠性如何揭露（最根本的問題）

條件單需要有東西**持續盯價、到價送單**。選項：券商端條件單（若 Shioaji 提供，需查證其
期貨條件單能力）vs 自建引擎。若自建：

- 現行報價是 **TAIFEX MIS 每 5 秒輪詢**——對停損觸發來說 5 秒在急行情中是很大的滑價窗口。
- 系統（VM／程式）**離線期間停損不會觸發**。這必須在 UI 明確揭露，
  否則使用者以為有保護而放大部位，實際保護不存在——**這比沒有條件單功能更危險**。
- 移動停損需要更頻繁的價格更新與狀態持久化（重啟後 trailing 水位不能歸零）。

#### T2 — 風控限額不得攔截保護性平倉單（已在現行程式碼驗證的真實陷阱）

`broker/risk.py::check_place` 對**所有**委託套用「今日委託次數上限」與「今日口數配額」，
**不分開倉／平倉**（risk.py:132-148 一路檢查 kill switch → 白名單 → 單筆口數 → 日筆數 → 日口數）。

最壞情境：行情急跌、停損單觸發，卻被自己的風控用「今日委託次數已達上限」拒絕。

→ 必須確立**全域原則：保護性平倉單（停損／停利，以及 F0/F1 的手動平倉）不受
   日配額、緊急停止、冷靜期攔截**。搭配「平倉口數不得超過持倉」的驗證（見 F0）防止濫用。

#### T3 — real 兩階段確認與自動觸發矛盾

現行 real 下單一律要求 confirm token（TTL 120 秒），但條件單觸發時**使用者不在場**，
不可能做二次確認。→ 需定義「設定條件單當下即完成預先授權」的機制，
且審計紀錄（OrderAudit）要能區分「人工下單」與「條件單觸發」。

#### T4 — 開倉型條件單 vs 冷靜期／緊急停止

條件單不只平倉：突破進場（到價**開倉**）也是條件單。若冷靜期只檢查「部位＋掛單」，
**站著的開倉型條件單就是第三種會生出部位的東西**——啟動冷靜期時必須一併揭露並暫停，
否則 F1 的空倉啟動條件會被繞過。（F0 啟動彈窗的揭露清單同理，要加上條件單。）

#### T5 — OCO 語意與部分成交

停利與停損同時掛著，其一觸發成交後**另一邊必須自動撤銷**（OCO），否則會反向開倉。
部分成交時，另一邊的口數要同步縮減。這是狀態機問題，錯了直接是錯單。

#### T6 — 滑鼠拖曳改單的誤觸風險

拖曳停損線＝**修改一張真實委託**。需要：拖曳結束後的確認步驟（或可撤銷），
以及與 real 改單兩階段確認的整合。KLineCharts 釘版 v9.8.12，overlay 拖曳能力需在該版驗證
（升版另有 v10 API 變更的既有約束）。

#### T7 — 契約月（又是它）

條件單是「站著的未來委託」，換月後觸發時指向哪個契約？
契約月缺口（共同前置條件第 2 點）不修，條件單跨換月就是錯單風險。

### 建議

條件單本質上是**風控的執行層**（停損就是風控），與 F0–F5 共用兩個地基：
「開倉／平倉的可判定性」與「保護性平倉優先於一切限制」。
建議把這兩個地基當成 F0 的一部分先定案，條件單的規格再另開文件細談
（觸發引擎的選型與可靠性揭露值得單獨一輪討論）。

### 引擎選型的決策授權（使用者 2026-08-28）

觸發引擎跑在哪裡（券商端條件單 vs 自建）**授權工程端決策**——使用者明示對技術引擎不熟，
交給工程師依 Shioaji 實際能力判斷。但 **T1 的可靠性揭露是產品驗收條件、不可退讓**：
無論選哪條路，「系統離線期間停損不會觸發」「輪詢間隔造成的滑價窗口」這類保護的真實邊界
必須在 UI 明確告知使用者——以為有保護而放大部位，比沒有這個功能更危險。
產品側的現階段內容（T1–T7 衝突檢核、bracket 模型、交互規則）至此已完備，
規格本體待工程端選型回饋後另開文件。

## 交互檢查 — 緊急停止／冷靜期 × 條件單（使用者 2026-08-28 指定進行）

> 兩套機制注定同時在場：停損本身就是風控的執行層，而停止／冷靜期管的正是「新委託」。
> 本節是產品層級的規則定案建議與風險情境；「規則」欄是建議採用的行為，供工程端評估回饋。

### 核心規則表：停止／冷靜期內，各類委託動作的處置

一切建立在「開倉／平倉可判定」（共同前置條件第 4 點）之上：

| 委託動作 | 停止／冷靜期內 | 依據 |
|---|---|---|
| 開倉（New，或淨效果為增加曝險） | ❌ 拒絕 | 兩個功能的本旨 |
| 平倉（Cover 且口數 ≤ 該方向持倉） | ✅ 放行，且**不佔日配額** | 平倉安全閥；保護性平倉不受攔截原則 |
| Auto 倉別 | ❌ 拒絕（fail closed） | 送出前無法判定開平（F0 L3） |
| 撤單 | ✅ 永遠放行 | 撤單不會生出部位 |
| 開倉掛單的改單（加量／改價） | ❌ 只准撤銷 | 改單是變相開倉（F0 L5／R3） |
| 平倉單／平倉型條件單的新設與改單 | ✅ 放行（口數驗證同上） | 保護能力不可鎖 |

「平倉口數 ≤ 持倉」必須在**送出時**與**條件單觸發時**各驗一次——觸發時持倉可能已經變了。

### 八個問題的結論

1. **兩者會不會互相衝突？** 會，衝突點固定三處：
   (a) **開倉型條件單 vs 禁止開倉**——觸發時在 RiskGuard 被擋，機制上安全；但 UX 必須把這些單
   呈現為「已暫停」，不能讓觸發靜默失敗（使用者以為單還活著）。
   (b) **平倉型條件單 vs 日配額**——現行 `check_place` 不分倉別套日筆數／口數限額（risk.py:132-148），
   急行情中停損單可能被自己的風控拒絕（T2）。必須先立全域原則：
   **保護性平倉不受日配額、緊急停止、冷靜期攔截**。
   (c) **real 二次確認 vs 自動觸發**——條件單觸發時使用者不在場（T3），
   設定當下即完成預先授權，稽核（OrderAudit）需區分「人工下單」與「條件單觸發」。
2. **冷靜期啟動後，既有停利／停損怎麼辦？** 啟動條件是 clean slate（無部位＋無掛單＋無任何
   有效條件單），所以**合法啟動後不存在既有停利／停損**。孤兒單（無部位卻掛著的停利／停損）
   在啟動彈窗中列出並要求先清理。冷靜期內若因場外部位需要保護，允許**新設平倉型條件單**
   （受口數驗證）。
3. **使用者可否修改既有停利／停損？** 常態下可以（含圖上拖曳）。停止／冷靜期內：
   平倉型可改（保護能力不鎖）——但「把停損往不利方向放寬」是典型的凹單行為，
   **放行＋記錄＋警示文案**，不禁止（自主權優先；此取捨已載明）。
   想要更嚴格的使用者可勾選 F5 的「**停損單向鎖定**」偏好（2026-08-28 新增：
   啟用後全時段禁止放寬、停損不可單獨撤銷），見 F5。開倉型一律只准撤。
4. **移動停損是否繼續運作？** 是。trailing 更新屬於平倉型委託的維護，停止／冷靜期內照常運作、
   不佔日配額；trailing 水位須持久化（重啟不歸零，T1 既有要求）。
5. **平倉單與反向開倉如何區分？** 以「octype ＋ 持倉狀態」雙重驗證：Cover 且口數 ≤ 該方向持倉
   才是平倉；**超量部分不靜默截斷**，明確拒絕並提供「改為 N 口平倉」的一鍵修正
   （靜默截斷會改變使用者意圖）。Auto 不做淨額猜測，停止／冷靜期內一律擋。
   ⚠ 契約月缺口未修前，換月前後的開平判定不可靠（共同前置條件第 2 點）。
6. **OCO／部分成交／加減碼的例外情境？**
   - **OCO 雙腿競態**：急行情中一根 5 秒報價區間同時穿過停利與停損 → 兩腿都觸發＝
     平倉之後**反向開倉**。對策：一腿成交立即撤另一腿；觸發時重驗持倉，第二腿驗不過即拒。
   - **部分成交**：一腿部分成交時，另一腿口數同步縮減，否則殘量足以反向。
   - **手動減碼**：平掉一部分後，掛著的停利／停損口數 > 剩餘持倉 → 引擎須在持倉變動時
     自動縮量（至少觸發時驗證要能擋下超量）。
   - **加碼**：加碼後既有停利／停損只蓋住舊倉。bracket 模型**已定案
     （使用者 2026-08-28）：部位層級**——一條停利／停損線管整個部位，加減碼時
     口數自動跟隨，圖上各只有一條線、拖曳調整最直觀。
     （「每筆進場各自帶」適合分批建倉各自結算的策略，日後有需求再作為第二模式評估，
     首版不做兩套。）
7. **繞過「禁止新增部位」的路徑（red-team 清單）**：
   假 Cover（L4 口數驗證擋）／Auto 倉別（L3 擋）／既有掛單成交（F1 啟動條件、F0 揭露＋批次撤銷）／
   開倉型條件單觸發（觸發時擋＋UX 暫停）／改單加量追價（L5 擋）／超量平倉淨反向（口數驗證擋）／
   OCO 雙腿競態（觸發重驗擋）／多裝置、直接打 API（帳戶層級狀態、server-side 攔截）／
   **場外通道（券商 App、直連 Shioaji）——唯一擋不住的**：誠實揭露範圍＋對帳偵測＋事後回顧呈現。
8. **API／自動策略／其他入口是否同步受限？** 是，立為系統不變式：
   **所有會產生委託的路徑（網頁表單、未來的 API、策略引擎、條件單觸發引擎、一鍵平倉鈕）
   一律經過同一個 `RiskGuard.check_place` / `check_update`**。
   現行架構已是如此（place／update 都在 adapter 內過 RiskGuard），未來任何新入口不得繞過。
   豁免以**規則類型**定義（保護性平倉豁免配額／停止），不以**入口**定義——不存在特權入口。

## 共同的前置條件

實作任何一項之前，建議先確認這三件：

1. **「總資金」的定義與來源**（F4 的分母，也會影響 F3 的門檻要用金額還是比例）。
2. **契約月欄位（安全性議題；使用者 2026-08-28 決定正式交付，完整推理如下）**：
   `db/models.py::Order`、`BrokerPosition` 與 `broker/types.py::Position` 都只有 `symbol`，
   沒有契約月；open 部位的唯一鍵是 `(user, broker, account, mode, symbol, direction)`，不含契約月。
   後果：換月之後，新契約的委託會與舊契約的未平倉部位被視為**同一個部位做淨額計算**
   （`position_tracker` 的 Cover/New 判定與 PnL 結算都以 symbol 為準），
   但券商端兩個契約不會互相平倉 → **帳上以為平掉了，實際上兩邊各留一口**。
   這個缺口在只有一個商品時也存在（**每次換月都會遇到**），不是多商品才需要處理。
   建議：`Order`／`BrokerPosition` 增加契約月（或完整契約代碼）欄位並納入部位 scope。
   它同時是 F2（一鍵清倉）的硬前置與 F6 T7 的前提。
3. **帶到期時間的帳戶狀態**：F1 的基礎，F3 觸發後若要「一鍵進入冷靜期」也需要它。
4. **「開倉／平倉」在風控層的可判定性**：F0 與 F1 的平倉安全閥都依賴這件事，
   而倉別 `Auto` 在送出前無法判定（見 F0）。這是兩個功能共用的前置決策，建議一次定清楚。
5. **全域原則：保護性平倉不受風控攔截**——日筆數／口數配額、緊急停止、冷靜期，
   一律放行平倉方向的委託（含未來條件單觸發的停損／停利）。
   現行 `check_place` 不分倉別套限額，是 F0／F6 共同要修的點（見 F6 的 T2）。

## 建議的順序

| 順序 | 項目 | 理由 |
|---|---|---|
| 1 | **F0（緊急停止改為只擋開倉）** | 既有功能的行為修正，範圍最小；且「不能平倉」在情緒失控情境下是實際危害 |
| 2 | F3（損益型提醒） | 資料與通知管道都現成，缺的只是規則與設定 UI |
| 3 | F1（交易冷靜期） | 使用者最想要的一項；需要新的帳戶狀態，但範圍清楚 |
| 4 | F5（操作摩擦） | 多半是既有機制的開關化 |
| 5 | F4（資金比例） | 等「總資金」定義確定 |
| 6 | F6（條件單）的**地基**（開平倉判定＋保護性平倉放行原則） | 與 F0 共用，建議合併定案；條件單本體另開規格 |
| 7 | F2（一鍵清倉） | 風險最高，且必須等契約月缺口修好 |
