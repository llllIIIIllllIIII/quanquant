## 一句話總結

下單的「後端安全」做得比「前端可感知度」紮實很多：兩階段確認、冪等鍵、風控上限、kill switch 都在，
但**畫面幾乎不告訴使用者「現在處在什麼狀態、剛剛那一下有沒有成功、這張單會送到哪裡」**。
在真錢下單的情境，這幾個資訊缺口比任何美觀問題都嚴重，建議優先修 P0 的 6 項。

## P0 — 會造成誤判或誤下單

### 1. 「正式 / 模擬」分頁永遠看不出哪個是選中的 【已重現】【讀碼確認】

`orders.html:74-75` 的 class 條件寫反了：

```jinja
<a class="{{ '' if mode == 'real' else 'contrast' }}" href="/orders?mode=real">正式</a>
<a class="{{ 'contrast' if mode == 'sim'  else '' }}" href="/orders?mode=sim">模擬</a>
```

- `mode == 'real'` → 兩顆都是 `''`
- `mode == 'sim'` → 兩顆都是 `contrast`

也就是**兩顆按鈕在任何情況下都長得一模一樣**（我在瀏覽器量過 computed style，背景/文字色完全相同）。
使用者無法判斷自己正在看哪一組委託列表。

對照 `journal.html:13-14` 是正確的寫法（第一顆的條件是 `f.mode == 'sim'`）。看起來是複製時把條件跟著標籤一起改了。

**建議**：修正條件，另外把選中態做成真正的 tab（現在 `.mode-tabs` 這個 class 在 CSS 裡根本不存在，
`app.css`/`tokens.css` 都沒有定義，等於三個頁面共用一個沒有樣式的容器）。

### 2. 頁面沒有任何地方標示「這張表單會送到哪個 mode」 【讀碼確認】

執行用的 mode 是 server 決定的（`app.state.order_service.mode`），
網址的 `?mode=` **只影響下方委託列表的過濾**，不影響下單（`routers/orders.py` 檔頭已寫明）。

結果是：使用者可能一邊看著「正式」列表、一邊送出模擬單（或反過來）。
目前唯一的線索是：真錢下單時會跳出確認框、以及非執行 mode 的列上不會出現操作鈕（`order_table.html:22`）——都太間接。

**建議**：表單標題旁固定一顆狀態徽章 `本次下單：模擬` / `本次下單：正式`（正式用 `--down` 系色，
並考慮整個表單加紅色外框），而把 mode 分頁改標成「檢視：正式／模擬」，明確區分「執行」與「檢視」。

### 3. 下單成功沒有任何可見回饋 【讀碼確認】【待實機驗】

成功路徑 `_place_success()` 只做兩件事：換掉 hidden 的 `client_order_id`、觸發列表刷新。
**沒有訊息、沒有 toast、按鈕沒有狀態變化**。

而且如果當下列表分頁不是執行 mode（見第 2 點），那筆新單**根本不會出現在列表裡** →
使用者的合理解讀是「沒送出」→ 再按一次。第二次是新的冪等鍵，會變成真的第二張單。

**建議**：成功時給明確回饋（「已送出：買 TXF 2 口 @24350，委託單號 xxx」）。
專案內已經有現成的 toast 元件可重用：`dashboard.html:395-398` 的 `.toast-stack` / `.alert-toast` + `chart.js:890`。

### 4. 錯誤訊息不會被清掉，會跟成功狀態並存 【讀碼確認】

`_form_error()` 把紅色 banner 塞進頁面上方的 `.form-error-slot`，
但成功路徑 `_place_success()` 沒有清空它。使用者失敗一次、修正後成功送出，
**那個紅色錯誤仍留在畫面上**，看起來像是又失敗了。

**建議**：成功回應時一併 OOB 清空 `.form-error-slot`（或把訊息改成有存活時間的 toast）。

### 5. 「取消委託」失敗時，訊息出現在使用者看不到的地方 【讀碼確認】【待實機驗】

取消／改單的錯誤同樣走 `_form_error()` → retarget 到**頁面最上方**的共用 slot。
但取消鈕在頁面下方的委託表格裡；使用者按下去、券商回錯誤，**畫面下半部完全沒有動靜**，
訊息在需要往上捲很多的地方。

**建議**：列表操作的錯誤就近顯示（該列下方展開一列，或改成 toast）。
改單表單已經有這個概念了（`_edit_form_error` 就是為了避免共用 slot 打架而做的），取消卻沒有。

### 6. 「取消」用瀏覽器原生 confirm，跟「改單」的體驗與風險等級都不對稱 【讀碼確認】

`order_table.html:28` 用 `hx-confirm="確定取消這筆委託？"`，跳出的是系統原生對話框（跟全站深色主題完全不同調），
內容也沒有告訴使用者要取消的是「哪一筆」（商品／方向／口數／價格都沒有）。
成功之後同樣沒有任何回饋。

**建議**：改用與改單相同的 modal，內容帶完整委託摘要；完成後給 toast。
（取消是不可逆動作，卻是全頁最陽春的一個確認。）

## P1 — 資訊不足，實際使用時很卡

### 7. 下單頁看不到任何報價 【已重現】

整頁沒有現價、買賣價、漲跌、量。要掛限價單得先切到儀表板看價格、記住、再切回來打字。

**建議**：頁面頂端重用既有的 `partials/quote.html` + `/quote/stream`（`dashboard.html:3-6` 就是現成範例），
並提供「帶入現價」、「±1 檔」快捷；理想是再加五檔報價。

### 8. 委託列表欄位不足以辨識一筆單 【已重現】

現有欄位：商品／方向／口數／價格／狀態／成交／操作。
**沒有時間、沒有委託單號、沒有價格類型／委託類型／倉別。**
同一天多筆同商品同方向的委託在畫面上長得一模一樣，出事時無法對帳。

資料其實都在（`models.py:262-278` 有 `created_at`、`price_type`、`order_type`、`octype`、`broker_order_id`），
時間格式化 filter 也有（`templating.py` 的 `dt` / `cst_time`）。

**建議**：至少補「委託時間」與「LMT/MKT・ROD/IOC/FOK・新倉/平倉」（後者可縮成一格小標籤），委託單號可用 hover/展開顯示。

### 9. 狀態欄是英文原始值 【已重現】

畫面上直接印 `submitted` / `partfilled` / `filled` / `cancelled` / `failed` / `unknown`（`order_table.html:19`）。
這違反專案「全站中文一律繁體台灣」的約束，也不是交易者的語彙。

**建議**：對照表（已委託／部分成交／全部成交／已取消／失敗／狀態不明）+ 顏色 badge，
`app.css:277` 已有 `.badge` 樣式可延伸。

### 10. 價格數字沒有格式化，市價單顯示「0」 【已重現】

同一欄同時出現 `24350.0`、`24300`、`0`（小數位不一致、無千分位）。
市價單的 price 在後端一律存 0（`_parse_order_price`），列表就直接印 `0` —— 看起來像 bug 或像掛到 0 元。

**建議**：套用既有的 `num` filter；`price_type == 'MKT'` 時價格欄顯示「市價」，成交後顯示成交均價。
部位表的均價同理。

### 11. 兩張表格沒有包 `.table-wrap` 【已重現】

`journal.html:37`、`stats.html:20` 都有包，下單頁沒有 →
少了卡片外框／圓角／`overflow-x` 橫向捲動／sticky 表頭。欄位一旦補齊（第 8 點），窄螢幕會直接被擠爆。

### 12. 買／賣藏在下拉選單裡 【已重現】

全頁**最關鍵、最不能點錯**的欄位，是一個預設「買」的 select，視覺上跟「倉別」同等權重。

**建議**：改成兩顆對比色按鈕（`--up` / `--down` token 已存在，表格裡的 `.dir.long/.short` 就是這組色），
送出鈕文案隨選擇變成「買進 2 口 @ 24350」——讓最後一眼就能複驗方向。

### 13. 風控上限完全不透明 【讀碼確認】

`config.py:66-68`：單筆上限 5 口、每日 20 口、每日 20 筆。
使用者只有在**被拒絕之後**才知道有這些限制。

**建議**：口數欄位旁標「上限 5 口」，頁面顯示「今日已用 3/20 筆、7/20 口」。

### 14. 兩階段確認框缺「取消」，也沒說 token 會過期 【讀碼確認】【待實機驗】

`confirm_dialog.html` 只有一顆「確認送出」。使用者反悔時沒有明確的退出路徑（只能不理它）。
另外確認 token 的有效期是 120 秒（`config.py:69`），畫面完全沒提示；
逾時後大概只會得到一個錯誤訊息，也沒有「重新產生確認」的按鈕。

**建議**：加「取消」按鈕、顯示倒數（例如「請於 2:00 內確認」）、逾時後就地提供重新確認。

### 15. 真錢下單的最後確認，內容不完整 【已重現於程式碼】

`confirm_dialog.html:1` 只列 商品／方向／口數／價格，
**缺價格類型、委託類型、倉別**——而這三項正是最容易選錯、後果最不同的欄位（例如 MKT+IOC vs LMT+ROD）。
市價單時這行會顯示「@ 0」。

**建議**：確認框列出完整委託內容（含 mode），市價單寫「市價」。

### 16. 改單 modal 不是真的 modal 【讀碼確認】【待實機驗】

`orders.html:97` 用 `<dialog :open="open">`（設 open 屬性）而非 `showModal()` →
沒有背景遮罩、ESC 關不掉、焦點沒有鎖在對話框內、位置也不是置中浮層。
另外 `@click="open = true"` 與 `hx-get` 同時發生 → 內容載入前會先看到一個空白框（沒有載入中狀態）。

（`journal.html:52` 是同一個模式，屬全站慣例；但在「改單」這個要快、要準的情境代價最大。）

### 17. agent 未連線時仍可按送出 【已重現】

`agent_status.html` 會顯示紅字「agent 未連線」，但下單表單完全不受影響，
使用者要按下送出、等一次失敗，才知道送不出去。

**建議**：未連線時停用送出鈕並直接寫「請先在本機啟動 agent」；狀態列給重試/說明連結。

### 18. 手機／窄螢幕：送出鈕在一屏半以下 【已重現】

寬度 <768px 時 Pico 的 `.grid` 會塌成單欄，7 個欄位各佔一列。
我在 ~555px 寬量到「送出」按鈕位於 y≈1004px，一般手機（812px 高）要捲動才看得到；
再往下才是分頁、狀態、委託表格（表格還沒有橫向捲動容器，見第 11 點）。

**建議**：手機版把商品/方向/口數/價格壓成兩欄、次要欄位（委託類型、倉別）收進「進階」摺疊，
送出鈕在小螢幕改成 sticky 底部。

## P2 — 一致性與打磨

19. **警示色硬編、且對比不足** 【已重現】：`agent_status.html:9` 與 `kill_switch_control.html:2,7` 寫死 `#c0392b`，
    沒用 `--down` / `--fall` token。在深色底（`--qq-bg: #020617`）上對比約 **3.7:1**，低於 WCAG AA 的 4.5:1 ——
    偏偏這是全頁最需要被看見的字。改用 `--down (#ea3943)` 即可改善，也才會跟著淺色主題走。
20. **inline style 取代 class**：kill switch 與 agent 狀態整塊用 inline style 寫版面，
    與專案 token/class 的做法不一致，改版時容易漏掉。
21. **商品只有一個選項**：`routers/orders.py` 寫死 `symbols: ["TXF"]`，一個選項的 select 是多餘的一次點擊；
    也還沒有近月／次月契約的概念（未來一定會用到）。
22. **可及性**：改單/取消是 `<a href="#" role="button">` 而非 `<button>`；錯誤 banner 沒有 `aria-live`；
    SSE 刷新表格時沒有任何提示（螢幕閱讀器與鍵盤使用者完全無感）。
23. **部位表太薄**：只有 商品／方向／口數／均價，沒有未實現損益、沒有「一鍵平倉」——
    現在要平倉得自己回表單選對邊方向 + 倉別「平倉」+ 口數，全靠人腦換算。
24. **成交沒有任何感知**：成交回報只會讓表格靜靜換一次內容，沒有 toast／聲音／桌面通知。
    專案已有 `BrowserNotifier` + alerts SSE toast 可重用。
25. **列表固定 100 筆**（`broker/repository.py:246`）：沒有分頁、沒有「已達上限」提示、沒有篩選（例如只看未成交）。

## 建議的處理順序

**第一批（高 CP，估計 1～2 天，全部是前端小改）**
1. 修 mode 分頁選中態（P0-1）

**第二批（體驗主升級）**
7. 下單頁嵌報價 + 帶入現價／±1 檔（P1-7）

**第三批（結構性）**
11. modal 改 `showModal()` + 載入狀態（P1-16）
12. 手機版版面（P1-18）
13. 部位表補未實現損益與一鍵平倉（P2-23）
14. 風控用量顯示（P1-13）
