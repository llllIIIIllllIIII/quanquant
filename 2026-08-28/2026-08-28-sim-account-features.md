# sim 虛擬保證金（模擬帳戶資金系統）— 功能規格

- 日期：2026-08-28
- 需求來源：介面主要使用者的產品構想，經逐項討論定案。
- **與其他交付文件的分工**：`2026-08-27-order-ui-ux-change-requests.md` 是 UI 調整、
  `2026-08-28-risk-control-features.md` 是風控功能；本文件是**模擬帳戶的資金系統**，
  核心決策已定案（見下），可直接排期實作；仍開放的細節在文末列出。
- **文件原則**：設計時考慮到的實務風險、可能的濫用方式與設計取捨一併保留（標示「設計紀錄」），
  不只記最後採用的規格。

---

## 為什麼要做（使用者原話）

> 目前模擬倉沒有保證金的數值概念，只有「績效統計」可以看結果，對於要練習交易的使用者，
> 真實感顯然不夠。我在想能否讓使用者自己設定初始保證金，然後讓使用者用自己設定的金額
> 去交易、累積資金或是被市場修理等等。

定位：**練習的真實感與紀律訓練**。sim 的成交本來就走券商模擬環境，缺的是「這些交易
發生在一個有限的資金池裡」的感受——資金會被占用、會不夠、會歸零。

## 現況盤點（實際翻程式碼的結果）

| 能力 | 位置 | 備註 |
|---|---|---|
| sim 成交手續費估算 | `config.py::order_sim_fee_per_lot`（預設每口 20） | fill 缺 fee 時按口數估算，累計進 round-trip |
| 損益數學 | `journal/pnl.py::compute_pnl` / `unrealized_pnl` | 純函式，含點值與 fee |
| round-trip 歷史留存 | `BrokerPosition`（closed 列永久保留）＋回寫 `Trade(source="shioaji")` | **輪次戰績用時間切片即可，不需新帳務表** |
| 點值 | `broker/position_tracker.py::_POINT_VALUES`（TXF 200 / MXF 50） | TMF 需補 |
| 下單稽核點 | `RiskGuard.check_place`（adapter 內） | 保證金檢核應掛進同一鏈 |

**沒有的**：任何保證金／權益／可用資金概念（real 也沒有——real 的分母已另定案走券商
margin API，見風控文件 F4）；「輪次」的資料模型。

## 核心設計：帳本事件＋衍生計算

**不存跑動中的餘額**，一切可重算，帳不會漂：

```
餘額     = 初始資金 + Σ已實現損益 − Σ手續費（自本輪起點切片）
權益數   = 餘額 + Σ未實現損益（mark-to-market，與 F3/006 同一套接線）
占用保證金 = Σ（每口原始保證金 × 未平倉口數）  ※多空鎖倉時收較大邊
可動用   = 權益數 − 占用保證金
```

- 帳本事件只有兩種：**開輪**（設定初始資金）與**重置**（結束本輪、開新輪）。
  沒有入金、沒有出金（使用者 2026-08-28 定案，理由見設計紀錄）。
- 保證金額（每口原始保證金，per symbol：TXF／MXF／TMF）為**可設定值**：
  出廠帶預設數字，UI 顯示目前使用的數值與「以期交所公告為準，請自行核對」提示。
  不做自動爬取（維運負擔與來源穩定性不划算，見設計紀錄）。
- **平倉永遠不檢核可動用**——平倉是釋放保證金，不是消耗。與風控文件「保護性平倉
  優先於一切限制」的全域原則同源。

## 已定案決策（使用者 2026-08-28）

| # | 決策 | 內容 |
|---|---|---|
| D1 | 擬真度目標 **L2（保證金檢核）**，工程可分兩期交付 | 第一期＝顯示層（餘額/權益/可動用接上畫面）；第二期＝開倉檢核（資金不足拒單）。L3（追繳、模擬強平）後期再議 |
| D2 | 初始資金**首次強制設定** | 第一次進 sim 資金帳時必須選一次：50 萬／100 萬／300 萬／自訂 |
| D3 | **不支援入金與出金** | 初始資金一輪定生死；資金要變只有重置開新輪一條路 |
| D4 | 重置需 **clean slate**（空倉＋無未成交掛單；條件單上線後含無有效條件單） | 與冷靜期 F1 的啟動條件同一套判定，可共用實作 |
| D5 | **爆倉不強平** | L2 下可動用 ≤ 0 自然鎖住開倉（檢核本來就過不了）、平倉永遠開放、畫面顯著警示；權益可為負、如實顯示；爆倉輪的紀錄完整保留 |

### 輪次（rounds）

- 重置＝結束本輪、開新輪（重新走 D2 的初始資金設定）。
- 歷史完整保留：戰績可**按輪篩選**（round-trip 與 Trade 都已留存，按輪次起訖時間切片）。
- 輪次資料模型最小化：`(user, started_at, initial_capital, ended_at?)` 即可，
  其餘全部衍生計算。
- 報酬率分母＝該輪初始資金（因 D3 無入出金，分母恆定、跨輪可比）。

## 設計紀錄：風險、濫用方式與取捨（保留勿刪）

- **D3 不支援入出金的取捨**：帳本最簡（兩種事件）、報酬率乾淨（分母固定）、
  **爆倉有重量**——被市場修理到歸零，這一輪就是結束了，只能帶著紀錄重來。
  代價：中途想「補錢續練」不行，必須重置歸零。這是刻意的：隨手補血會把
  「資金管理」這門課從練習裡拿掉。
- **D5 爆倉不強平的取捨**：L2 沒有強平引擎，權益可能持續惡化成負數——如實顯示負數
  本身就是教育（真實世界這叫超額損失）。自動強平屬 L3，其複雜度（市價/限價、部分成交、
  失敗重試）與風控文件 F2 同級，不在本規格。
- **保證金額手動維護的取捨**：期交所會調整保證金，手動設定值會過期 → UI 必須顯示
  「目前使用的數值」讓使用者自行核對；不爬期交所網站（來源格式不穩、為 sim 練習
  功能背上爬蟲維運不划算）。
- **鎖倉收較大邊 vs 兩邊都收**：較大邊貼近期交所實務（建議）；工程若第一期嫌複雜，
  可先兩邊都收（保守、不會高估可動用），但要在 UI 註明「鎖倉暫按雙邊計收」。
- **繞過風險檢視**：sim 檢核唯一的「繞過」是重置——這是設計內行為（D4 已要求 clean
  slate，帶著爛部位洗牌不可能）。檢核掛在 RiskGuard 單一稽核點，UI 停用只是體驗層。
- **Auto 倉別與檢核**：Auto 送出時判不出開平（風控文件 F0 的既有結論）。保證金檢核
  對 Auto 單以**最壞情況（當作開倉）**計可動用——寧可誤擋、不可少收。空倉時 Auto
  本來就是開倉；有倉時使用者若意在平倉，選「平倉」即不受檢核。

## 驗收條件

**第一期（顯示層）**：

- [ ] 首次進入 sim 資金功能時，強制完成初始資金設定（50 萬／100 萬／300 萬／自訂），
      設定前不顯示任何資金數字。
- [ ] 006 精簡條的「可動用保證金」在 sim 顯示真數字（取代「規劃中」占位）；
      real 仍走券商 margin API（F4 之接線）。
- [ ] 有一個「模擬帳戶」區（建議在帳戶設定頁）顯示：本輪初始資金、餘額、權益數、
      占用、可動用、本輪起始日；並提供重置入口與每口保證金額的設定/檢視。
- [ ] 權益數含未實現損益、隨報價更新（與 006 浮損同一接線）。
- [ ] 重置需 clean slate，否則拒絕並列出實際持倉／掛單（同 F1 啟動彈窗的呈現邏輯）。
- [ ] 重置後戰績可按輪查看，歷史輪紀錄不消失。

**第二期（檢核層）**：

- [ ] sim 開倉委託在送出時檢核「所需保證金（口數 × 每口原始保證金）≤ 可動用」，
      不足即拒單，拒單訊息含缺口金額（「需 36 萬、可動用 28.5 萬」）。
- [ ] 平倉委託不受此檢核。Auto 按開倉從嚴計。
- [ ] 檢核掛在 RiskGuard 鏈（單一稽核點不變式），僅 sim 模式生效。
- [ ] 可動用 ≤ 0 時下單頁明確顯示原因（不是按了才知道）；平倉側維持可用。

### 不要動到的部分

- real 模式的任何行為（real 保證金走券商 API，屬 F4 範疇）。
- 既有 sim 成交流程（Shioaji 模擬環境）、`BrokerPosition` 帳務、round-trip 結算數學。
- 手續費估算沿用 `order_sim_fee_per_lot`；期交稅若要納入，併進每口費用估算即可，
  不另立稅目（見開放事項）。

## 開放事項（不擋第一期）

- 每口保證金額的編輯 UI 落點（建議：帳戶設定頁「模擬帳戶」區，與初始資金/重置同區）。
- 期交稅（十萬分之二）要不要併入每口費用估算——建議直接把 `order_sim_fee_per_lot`
  的預設值視為「費＋稅概算」，不另立欄位。
- TMF 點值需補進 `_POINT_VALUES`（微台每點 NT$10）。
- 風險指標（權益/占用 %）的顯示——L3 前可先當純參考數字顯示，非本規格必要項。

## 給工程師的話

第一期幾乎全是「切片計算＋顯示」：資料都在（round-trip、fee、unrealized_pnl 純函式），
新增的只有輪次表與設定值。第二期的檢核請掛進 RiskGuard 鏈、遵守「平倉不檢核」。
若你對鎖倉計收、Auto 從嚴、或輪次模型有不同看法，直接回饋——本文件的成本評估
來自測試端讀碼，可能漏掉你那邊的脈絡。
